# Onboarding Acceptance — Reliable Employee & User Creation

## Problem

When a candidate clicks "Yes, I Accept" on the onboarding offer, the backend is supposed to:

1. Mark onboarding as accepted (`onboardingAcceptedAt = NOW`)
2. Update employee request status to 7 (completed)
3. Convert the candidate into an `Employee` row
4. Create a `User` account (role = Employee) and email login credentials
5. Notify the inviter HR

In production, **steps 3 and 4 silently fail every single time**. As of 2026-04-07, 5 candidates have accepted onboarding (IDs 35, 45, 48, 50, 53) and **none of them have employee or user records**. HR currently has no way to fix this — there is no manual "convert to employee" feature in the HR app.

### Root cause

`convertToEmployee()` is called as fire-and-forget at `recruitment-hris-api/src/services/candidateService.ts:1584`. The error it throws is hidden inside a `.catch(err => console.error(...))` block.

The actual error, captured by running `convertToEmployee(50)` in isolation:

```
PrismaClientKnownRequestError:
Invalid `prisma.employee.create()` invocation in
src/repositories/employeeRepository.ts:219:42

Null constraint violation on the fields: (`superior_id`)
```

**Schema mismatch between Prisma model and live MySQL:**

| Column | Prisma declaration | MySQL DDL | Effect |
|---|---|---|---|
| `employee_list.superior_id` | `superiorId Int? @map("superior_id")` | `superior_id int NOT NULL` | INSERT always rejected because `convertToEmployee` never sets a superior |
| `employee_list.employee_name` | `employeeName String?` | `employee_name varchar(255) NOT NULL` | OK today (always set) but a latent footgun |
| `employee_list.employee_status` | `employeeStatus String?` | `employee_status varchar(45) NOT NULL` | OK today (always set to `'active'`) but a latent footgun |
| `employee_list.uuid` | `uuid String?` | `uuid char(36) NOT NULL` | OK today (always generated by repository) but a latent footgun |
| `users.name` | `name String?` | `name varchar(255) NOT NULL` | OK today (always set) but a latent footgun |

The combination of (a) silent fire-and-forget error handling, (b) Prisma schema lying about nullability, and (c) HR having no manual fallback means the bug has been invisible to the team.

## Decision Summary

| Decision | Choice | Reasoning |
|---|---|---|
| Trigger | Automatic on accept (no HR approval) | Same as current intent — accept = onboarded |
| Execution model | **Synchronous, transactional** (await before responding to candidate) | Eliminates silent failures. If conversion fails, the whole accept-onboarding action rolls back so HR sees the candidate still in "awaiting acceptance" and can retry. |
| `superior_id` resolution | **Default `0`** (no superior) | User decision. HR sets superior manually later via Employee management. No department-manager lookup needed. |
| Schema fix | **Update Prisma schema to match MySQL** (`superiorId Int @default(0)`) | Single source of truth. Prevents the same class of bug for the other NOT NULL columns. |
| Welcome email | **Fire-and-forget after the transaction commits** | Email failure should not block conversion or rollback the transaction; failures get logged + HR notified. |
| HR notifications | Sukses → notif berisi `employee_id`. Gagal → notif urgensi tinggi berisi error message. | Visibility into both happy and sad paths. |
| Backfill of 5 existing affected candidates | **Out of scope** — user will test manually with fresh candidates after the fix lands | Avoids touching production rows automatically. The user is comfortable doing manual recovery later if needed. |
| HR-side manual retry endpoint | **Out of scope** | The new sync transactional flow makes retry unnecessary. |

## Design

### New flow (happy path)

```
POST /v1/candidate-auth/accept-onboarding
  └─ candidateAuthController.acceptOnboarding
       └─ candidateService.acceptOnboarding(candidateId)
            ├─ Preflight (no DB writes)
            │   ├─ Load onboarding by candidateId        → must exist
            │   ├─ Reject if onboardingAcceptedAt is set → 409 already accepted
            │   ├─ assessments.hasPassedAllAssessments() → must be true
            │   ├─ onboarding.isOnboardingComplete()     → must be true
            │   ├─ Load candidate detail (job_title_id, employee_request_id)
            │   ├─ Load employee request (departmentId)
            │   └─ Resolve "Employee" roleId from role_access (must exist)
            │
            ├─ Build payload (no DB writes)
            │   ├─ EmployeePayload  (from candidate + onboarding + detail)
            │   ├─ UserPayload      (email, hashed password, roleId, name)
            │   └─ generatedPassword (kept in memory for the welcome email)
            │
            ├─ prisma.$transaction(async tx => {           // ⇐ ALL writes here
            │     1. tx.candidate_recruitment_onboarding.update — set onboardingAcceptedAt
            │     2. tx.employeeRequest.update              — statusEmployeeRequest = 7
            │     3. tx.employee.create                     — superior_id = 0
            │     4. tx.user.create                         — link employee_id, role = Employee
            │     return { employeeId, userId }
            │  })
            │
            ├─ Post-commit side effects (errors logged, never throw)
            │   ├─ emailService.sendWelcomeEmail({ email, name, password: generatedPassword })
            │   ├─ sendRecruitmentNotification(ONBOARDING_ACCEPTED, inviter, employeeId)
            │   └─ structural-position auto-fill if Employee.title set
            │
            └─ Return updated onboarding payload
```

### Sad path

If any preflight check fails → throw a typed error (`NotFoundError`, `BadRequestError`, `ConflictError`) → controller maps to HTTP error → candidate sees toast and the onboarding stays in "awaiting acceptance".

If the transaction fails (DB error, FK violation, etc.) → Prisma rolls back **all four writes**, including the `onboardingAcceptedAt` timestamp. Candidate sees a generic error toast ("Something went wrong, please contact HR") and the inviter HR receives a `CONVERSION_FAILED` notification with the exception message. The candidate can safely click "Yes, I Accept" again after the underlying issue is resolved.

If the transaction succeeds but a post-commit side effect (welcome email, HR notification, structural-position fill) fails → log the error and continue. The candidate is fully onboarded; HR can resend the email or fix the structural position later.

### Schema fix in `recruitment-hris-api/prisma/schema.prisma`

Update `Employee` model so Prisma matches MySQL reality:

```prisma
model Employee {
  // ...
  superiorId        Int     @default(0) @map("superior_id")              // was Int?
  uuid              String  @unique @db.Char(36)                         // was String?
  employeeName      String  @map("employee_name") @db.VarChar(255)       // was String?, size corrected
  employeeStatus    String  @map("employee_status") @db.VarChar(45)      // was String?, size corrected
  // ...
}
```

Update `User` model:

```prisma
model User {
  // ...
  name  String  @db.VarChar(255)  // was String?, size corrected
  // ...
}
```

Then run `npx prisma generate` (no migration needed — schema already reflects the production DB; we are aligning Prisma to the existing schema, not the other way around).

### Idempotency

The transaction must be safe to retry.

1. **Pre-transaction guard:** if `onboardingAcceptedAt` is already set OR if an `Employee` with the candidate's email already exists, throw `ConflictError("Onboarding already accepted")` before opening the transaction. The candidate UI handles 409 by reloading the onboarding state and showing the success screen.

### Repository pattern compliance (recruitment-hris-api/CLAUDE.md)

Per project rules: Prisma calls must live inside repositories, services orchestrate. The transaction boundary is owned by a new function:

```ts
// repositories/onboardingConversionRepository.ts
export type ConversionPayload = {
  candidateId: number
  onboardingId: bigint
  employeeRequestId: number
  employee: Prisma.EmployeeUncheckedCreateInput
  user: Prisma.UserUncheckedCreateInput
}

export async function acceptOnboardingAndConvert(
  payload: ConversionPayload
): Promise<RepositoryResult<{ employeeId: number; userId: number }>>
```

This function owns the `prisma.$transaction` call and all four writes. The service builds the payload (validation, mapping, password hashing, role lookup) and hands it to the repository. This keeps Prisma access localized while still allowing a single atomic transaction.

The existing `acceptOnboarding` in `candidateService.ts` is rewritten to:

1. Call `assessments.hasPassedAllAssessments()` and `onboarding.isOnboardingComplete()` (preflight, no writes).
2. Gather candidate / detail / request / role data (read-only repos).
3. Build the `ConversionPayload` (pure function, easy to unit test).
4. Call `onboardingConversionRepository.acceptOnboardingAndConvert(payload)`.
5. After it commits, fire-and-forget the welcome email + HR notifications.
6. Return the refreshed onboarding entity.

`convertToEmployee()` and the fire-and-forget block at `candidateService.ts:1584` are removed.

### Welcome email

Today the welcome email is sent from inside `userRestService.createUser()` (also fire-and-forget). For the new conversion path we **do not** call `userRestService.createUser()` at all — the user row is created directly inside the `prisma.$transaction` via `tx.user.create`. Once the transaction commits, `candidateService.acceptOnboarding` calls `emailService.sendWelcomeEmail()` itself, passing the plain password generated before the transaction (held in a local variable).

`userRestService.createUser()` and `userRestRepository.create()` are **not modified** — they keep their existing behavior for the HR-driven manual user creation flow.

## Files Modified

### `recruitment-hris-api/`

| File | Change |
|---|---|
| `prisma/schema.prisma` | Align `Employee` and `User` models with MySQL NOT NULL columns; add `@default(0)` to `superiorId` |
| `src/repositories/onboardingConversionRepository.ts` | **NEW** — owns the `prisma.$transaction` for accept + create employee + create user |
| `src/services/candidateService.ts` | Rewrite `acceptOnboarding()` to use the new transactional repo. Delete `convertToEmployee()` and the fire-and-forget block. Hash password and resolve Employee role inside the service before calling the repo. Send welcome email + HR notification post-commit. |
| `src/services/employeeService.ts` | No behavior change. `autoCreateUserForEmployee()` continues to serve the HR-driven manual employee-creation flow. The conversion path bypasses `createEmployee()` entirely and writes Employee + User directly inside the transaction. |
| `src/repositories/employeeRepository.ts` | `create()` mapping defaults `superiorId` to `0` so HR-driven employee creation also satisfies the NOT NULL constraint. |

### `candidate-recruitment-hris/`

| File | Change |
|---|---|
| `src/services/candidate-profile.service.ts` | `acceptOnboarding()` already handles errors via try/catch; verify the error message surfaces a friendly toast when the backend returns 5xx so the candidate knows to contact HR. |

No frontend UI changes needed beyond verifying the error toast text.

## Out of Scope

- Automatic backfill of the 5 already-affected candidates — user will test the fix manually with fresh candidates
- HR-side "manual convert" UI in `recruitment-hris` (the new sync flow eliminates the need)
- Department-manager auto-resolution for `superior_id` (user chose `Default 0`)
- Migration to add `superior_id NOT NULL` to MySQL — it is already NOT NULL in production
- Any change to the assessment / interview / MCU flows

## Testing Plan

1. **Unit / integration test in `recruitment-hris-api`:**
   - `onboardingConversionRepository.acceptOnboardingAndConvert` happy path → asserts all 4 rows written and returns `{ employeeId, userId }`
   - Same call rolled back when employee insert violates a constraint → asserts onboarding row, employee request status, and user row are all unchanged
2. **Manual end-to-end (user-driven):**
   - Create a fresh candidate, walk through assessments + interviews + MCU + onboarding
   - Click "Yes, I Accept" in the candidate app
   - Verify in DB: `employee_list` row exists with `superior_id=0`, `users` row exists with role = Employee linked via `employee_id`, candidate's `onboarding_accepted_at` is set
   - Verify candidate received welcome email with login credentials
   - Verify HR (inviter) received `ONBOARDING_ACCEPTED` notification carrying the new `employee_id`
   - Repeat once more to verify idempotency: re-clicking "Yes, I Accept" should return 409 and not create duplicates
3. **Negative test:**
   - Manually break a precondition (e.g. set an MCU result to FAILED) and click "Yes, I Accept"
   - Verify the candidate sees an error toast and `onboarding_accepted_at` stays NULL — proves rollback works
4. **Regression:** HR-driven employee creation in the HR app still works (still uses `employeeService.createEmployee` + `autoCreateUserForEmployee`).
